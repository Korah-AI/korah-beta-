# Problem
Both codebases already use Firestore, but they do not share the same document contract\. The web app writes string\-based session and study\-item documents through `korah-web/korah-bot/app/data/firestore-store.js (33-295)` and `korah-web/korah-bot/study/new.html (637-659)`, while the iOS app reads and writes `UUID`/`Date`\-backed Codable models through `korah-beta- 2/Korah (Beta)/Managers/FirestoreStudyService.swift (33-171)`, `korah-beta- 2/Korah (Beta)/Managers/FirestoreConversationService.swift (32-95)`, `korah-beta- 2/Korah (Beta)/Views/Conversation/ConversationModels.swift (9-86)`, `korah-beta- 2/Korah (Beta)/Views/Study/Flashcards/FlashcardModels.swift (66-73)`, and `korah-beta- 2/Korah (Beta)/Views/Study/StudyModels.swift (3-102)`\. Because IDs, timestamps, and payload shapes differ, direct sync between the two clients is unreliable\.
## Current state
The web repo already has a single Firestore boundary in `korah-web/korah-bot/app/data/firestore-store.js (33-295)` and wires realtime updates into the chat UI in `korah-web/korah-bot/app/korah-chat.js (2087-2156)`\. The iOS repo already starts Firestore listeners at app launch in `korah-beta- 2/Korah (Beta)/KorahApp.swift (85-107)` and exposes centralized services for study items and conversations in `korah-beta- 2/Korah (Beta)/Managers/FirestoreStudyService.swift (33-171)` and `korah-beta- 2/Korah (Beta)/Managers/FirestoreConversationService.swift (32-95)`\. Study items are already separated into `flashcardSets`, `studyGuides`, and `practiceTests` on both sides, so that part is structurally close\. Conversations are farther apart: the web app stores an entire session document, while iOS models conversations and messages differently and still keeps scan image files on\-device in `korah-beta- 2/Korah (Beta)/Views/Conversation/ConversationManager.swift (99-126)` and `korah-beta- 2/Korah (Beta)/Views/Scanner/ScanView.swift (1576-1615)`\.
## Scope and non\-goals
This plan implements forward\-looking sync for study items and conversations across both apps\. Legacy conversation migration is out of scope\. The implementation should not block on cross\-device scan image sync; text\-first conversation sync should ship first, and Firebase Storage\-backed attachments can be added as a follow\-up\.
## Proposed architecture
Study items should continue using the existing per\-type collections: `users/{uid}/flashcardSets`, `users/{uid}/studyGuides`, and `users/{uid}/practiceTests`\. A shared v2 schema should be introduced for all new writes, with `schemaVersion`, stable UUID\-string document IDs, Firestore timestamps, shared metadata \(`title`, `description`, `subject`, `tags`, `source`, `createdAt`, `updatedAt`, `lastOpenedAt`\), and collection\-specific payload fields\. Web UI code can keep consuming normalized plain objects, but `korah-web/korah-bot/app/data/firestore-store.js` should become the only place that translates between Firestore docs and the in\-memory shape the pages use\. On iOS, Firestore services should stop decoding directly into the current view models and instead map Firestore DTOs into app models inside the service layer\.
Conversations should move to a thread\-based schema instead of rewriting a single document with a growing `messages` array\. The cleanest cutover is a new top\-level collection such as `users/{uid}/conversationThreads/{threadId}` with a `messages` subcollection\. Each thread document should contain summary metadata \(`schemaVersion`, `title`, `kind`, `subjectMode`, `createdAt`, `updatedAt`, `lastMessagePreview`, `messageCount`\), and each message document should contain the message body \(`role`, `text`, `createdAt`, optional `studyItemRef`, optional `attachmentPath`\)\. This avoids document\-size limits, reduces overwrite conflicts, and lets both clients stream or append messages incrementally\. Because old conversations do not matter, the new thread model can launch without any backfill of the legacy conversation documents or local files\.
## Implementation phases
### Phase 1: Define the shared sync contract and client adapters
Write down the canonical v2 Firestore shapes for `flashcardSets`, `studyGuides`, `practiceTests`, `conversationThreads`, and `conversationThreads/{threadId}/messages`\. Standardize on UUID strings for document IDs so the web app can generate IDs with `crypto.randomUUID()` and the iOS app can still convert them into `UUID` where needed\. Standardize on Firestore timestamps at the storage layer, while keeping platform\-friendly representations at the UI boundary\. On the web side, update `korah-web/korah-bot/app/data/firestore-store.js` so every read returns normalized objects and every write serializes into the v2 contract\. On the iOS side, add DTOs inside the Firestore services and map them into the existing app\-facing models so the rest of the SwiftUI code does not have to talk to raw Firestore payloads\.
### Phase 2: Complete study\-item sync using the shared schema
Keep the current study\-item collection names, but make both clients write the same v2 payloads\. Update the web create, edit, detail, and sidebar flows in `korah-web/korah-bot/study/new.html (637-705)`, `korah-web/korah-bot/study/item.html (1541-1579)`, `korah-web/korah-bot/study/guide.html (1115-1137)`, `korah-web/korah-bot/study/test.html (1437-1452)`, and `korah-web/korah-bot/study/js/sidebar.js (159-260)` so they stop inventing web\-only shapes and instead use the shared v2 model\. Update `korah-beta- 2/Korah (Beta)/Managers/FirestoreStudyService.swift (87-171)` and the creation/edit entry points in the SwiftUI study flows to read and write the same contract\. Preserve the existing UI\-level distinctions between flashcards, guides, and practice tests, but make the Firestore boundary consistent enough that a study item created in one client can be opened, edited, and deleted from the other client without shape conversion failures\.
### Phase 3: Implement thread\-based conversation sync
Introduce the new conversation thread repository on both clients\. On the web side, replace the current whole\-session document writes in `korah-web/korah-bot/app/korah-chat.js (53-80)`, `(891-903)`, and `(1749-1798)` with thread summary updates plus message appends\. On the iOS side, replace the current whole\-conversation Firestore writes in `korah-beta- 2/Korah (Beta)/Views/Chat/ChatViewModel.swift (334-362)` and `korah-beta- 2/Korah (Beta)/Views/Scanner/ScanView.swift (1576-1615)` with the same thread\-and\-message approach\. `korah-beta- 2/Korah (Beta)/Managers/FirestoreConversationService.swift` should be expanded to load thread summaries for history screens and fetch message subcollections for detail screens\. Because legacy conversations are intentionally out of scope, no time should be spent trying to transform the old web session docs or the old local iOS conversation files\.
### Phase 4: Handle scan attachments as a separate sync layer
Text conversation sync should ship first\. For scan conversations, message text and metadata can be synced immediately, but image attachments should remain a separate phase because iOS currently stores them as local files\. If scan attachments need to work across devices, upload them to Firebase Storage, persist the Storage path on the message document, and teach both clients to resolve that path when rendering scan messages\. Until that is implemented, the thread schema should allow `attachmentPath` but both clients should treat it as optional and non\-blocking\.
### Phase 5: Validation, rollout, and cleanup
Validate the new contract with a small set of round\-trip scenarios: create a flashcard set on iOS and open/edit it on the web app; create a study guide on the web app and open/delete it on iOS; start a text conversation on one client and continue it on the other\. Confirm that thread histories sort correctly by `updatedAt`, that deletes propagate across clients, and that the web app no longer depends on ISO\-string timestamps inside Firestore\. Once both clients are stable on the new schema, remove the remaining code paths that assume legacy web\-only or iOS\-only persistence formats from the Firestore boundaries, while leaving UI code as untouched as possible\.
## Expected outcome
At the end of this work, both codebases will share a single Firestore contract for study items and conversations\. Study items will sync through the existing per\-type collections with a consistent schema, and conversations will sync through a thread\-plus\-messages model that is safer than the current single\-document session approach\. The resulting architecture keeps the existing app structures recognizable, minimizes UI churn, and avoids wasting time on legacy conversation migration that is no longer important\.
